what is it, really?

AI apps can talk. Keel lets them do things.

An AI app is good at chatting. To look something up, save a note or make a booking, it needs tools. Keel builds those tools for you. A set of tools like this is called an MCP server.

MCP is a plug.

Any AI app with the socket can use any tool with the plug. MCP is the name of that plug.

You write a list.

One file says which tools exist and what the rules are. Keel reads it and builds everything else.

Keel keeps the rules.

Who is allowed to use each tool, what needs a person to say yes, and a record of what happened.

what an MCP agent is

A loop: think, pick a tool, use it, repeat.

An MCP agent is an AI model going round a loop. It asks an MCP server which tools exist (tools/list), uses one (tools/call), reads the result and decides what to do next.

What can it see?Which tools are shown to the AI, and when. This is called tool visibility.
What may it do?Which actions it can take by itself and which need a person. This is execution authority.
Who decides the order?The AI guessing each next step, or a fixed set of steps. This is control flow.
the problem, and the fix

Plain MCP has five weak spots. Keel closes them.

Each row shows what goes wrong on the left and what Keel does about it on the right.

TOO MANY TOOLS AT ONCE

Every tool is loaded at the start.

MCP puts every tool's description in front of the AI when the session begins. That costs more with each tool you add, and the AI gets worse at picking the right one.

→
PROGRESSIVE DISCLOSURE

Only the tools for this step.

Keel filters tools/list by workflow stage and loads the rest only when they are needed.

THE SAME DATA, PAID FOR TWICE

Every in-between result passes through the AI.

When one tool's output feeds the next, the AI reads it each time. The same data is counted and paid for again and again.

→
SERVER-SIDE COMPOSITION

The server does the middle steps.

Keel chains tools on the server, using a declared recipe or a sandbox. In-between results stay out of the AI's view and only the final answer comes back.

ORDER LEFT TO CHANCE

The AI guesses what comes next.

Nothing guarantees the steps happen in the right order. Running code written by the AI saves cost, but it can run anything, is open to trick instructions and is hard to audit.

→
A STATE MACHINE

Fixed steps where order matters.

Keel enforces the move from one stage to the next, so step two cannot happen before step one. Open-ended tasks are still left to the agent.

LONG JOBS GO DARK

No way to ask "is it done yet?"

The protocol has no status check and no way to collect a result later, and a server cannot shape how work is handed out.

→
TASKS AND SUBAGENTS

A ticket for every long job.

Keel gives long calls a durable handle you can poll and collect from. It hands small jobs to subagents that get their own clean memory and only what they need.

NOBODY CHECKS THE SERVER

Trust is taken on faith.

An MCP server can come from anywhere, and nothing verifies it before it runs.

→
VERIFIED BUNDLES

Checked before it runs.

Keel packs each agent into one bundle, fingerprints it and gives it a trust score. It refuses to publish or load one that fails.

the great parts

One file switches all of this on.

Each block below is a few lines in agent.yaml. You describe what you want. Keel does the wiring.

stages: · progressive disclosure

Only the tools for right now.

Fifty tools at once confuse an AI. Stages show it a few at a time, and it must finish one step before the next one opens. It cannot reach the checkout before the basket is filled.

stages:
  intake:
    tools: ["echo"]
    skills: ["getting_started"]
  working:
    tools: ["echo"]
    ui: ["ui://hello"]
transitions:
  intake: ["working"]

Little screens inside the chat.

Some answers are better shown than told. Declare a widget once and the AI app can show a card, a form or a table, so a person can see the choices and pick one.

      mode: html
      display: ["inline"]

skill:// · skills

How-to notes the AI reads first.

Write instructions in a plain text file called SKILL.md. Keel serves it three ways: something the app can read, a tool the AI can call, and a command a person can type. The AI is told to read the right note before it acts.

skills:
  - path: skills/getting_started/SKILL.md
    autoload: stage:intake
# the address the AI app reads
skill://greeting/SKILL.md
flows: · recipes

Many steps, one call.

A flow is a recipe: do this, then that, then choose. Keel runs the whole recipe on the server in one go, so the AI does not have to remember the order or spend effort on each step.

flows:
  - file: flows/hello.yaml
# inside the recipe
nodes:  entry → transform → switch → exit
# the AI runs it with one tool
run_flow
entities: · records

Describe a record. Get the tools.

Tell Keel what a ticket, a booking or a contact looks like. It makes the tools to create, read, change, list, search and delete one. You write no code for any of them.

entities:
  - schema: entities/ticket.schema.json
# Keel makes these for you
create_ticket  get_ticket
update · list · search · delete
presentation: brief

Short answers first.

An AI can only hold so much in its head. A long list comes back as a short summary with a handle to fetch the full record. Twenty rows cost a few hundred characters, and nothing is lost.

# every read tool accepts this
presentation: "brief"   # the default
# the reply carries a handle:
# "call get_ticket with this id
#  for the full record"

What the AI app actually sees is small and never changes shape. It sees these six tools, plus only the ones the current stage allows:

list_capabilitiesuse_skillrun_flowread_resourceset_stagestate_set
servers:

One front door

Put many tool servers behind one. The AI app sees a single, tidy list.

policies:

Rules the AI cannot skip

Your business rules are checked before every tool call. The AI can ignore advice. It cannot get past these.

audit

A diary nobody can edit

Every action is written down in a chain, so a changed entry would show.

tasks · triggers · subagents

Timers, long jobs and sidekicks

Run a job on a schedule, let slow work finish in the background, and hand small jobs to an agent with fewer powers.

keel eval

Tests with no internet

Check that your agent still behaves, without an API key or a network connection.

keel publish

A safety check before sharing

Keel scans the bundle for leaked passwords and loose ends. It refuses to publish one that fails.

built for travel

Find it. Book it. Pay for it.EARLY VERSION

A trip has moving parts: a flight, a stay, a tour. Keel includes a shared rulebook for them, called the Agentic Travel Protocol (ATP). It stays switched off until you turn it on.

01

Know what is possible

Each supplier says whether an agent may search, hold or book. The agent only promises what can be done.

02

Payments with a limit

The agent pays with a virtual card tied to the approved booking, with a set amount and an end date.

03

No booking system? Start anyway

A rate sheet or a PDF can become an offer. Where nothing is live, the operator confirms before the booking goes ahead.

04

Considerate searching

Suppliers limit how often you may look without booking. Keel avoids asking the same question twice.

05

Booked is a beginning

Watch a booking for a lower price or a delay, and act within the terms of the trip.

06

Your deals, your rules

Bring your own supplier arrangements. Contracts and business rules are checked before an agent acts.

atp:// · the travel protocol

Three calls carry a whole trip.

Open one purchase, hold each part, then confirm them all together. The last call is refused unless a person has said yes, and that yes can only be used once.

atp_CreateTripTransaction
  # open one purchase for the whole trip
atp_CreateReservation
  # hold one part: flight, stay or tour
atp_CommitTripTransaction
  # confirm every part, after a yes
agent.yaml

Switch it on in a few lines.

Name each supplier and which of its tools do the searching and the holding. Keel adds the travel tools and the safety gates.

atp:
  enabled: true
  version: "0.3"
  suppliers:
    sabre:
      server: flights
      ops:
        search: sabre_search_flights_roundtrip
        hold: sabre_hold

ATP follows a draft specification (version 0.3) and may change. Card controls depend on the card programme used.
