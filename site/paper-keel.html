keel: From supplier documents to checked actions

What must be true before an AI agent can use a travel tool?

ABSTRACT

A supplier API describes operations. A document describes intentions. Neither, on its own, gives an AI agent permission to act. This paper examines keel as the boundary between those descriptions and an executable travel action. We separate the tool’s contract, its declared capability, the caller’s authority and the evidence returned by the call. The supplied code includes API compilation, a separate document-extraction path, checks around tool calls and MCP-Apps interfaces. It also exposes limits: some tools describe a contract without a live connection, and deployment settings determine which checks are enforced. The contribution is a practical account of how these boundaries fit together, plus a test plan for the cases most likely to mislead a user.

THE CENTRAL IDEAA description can suggest a tool. Only a checked connection can establish what that tool can actually do.

1. The gap between “can describe” and “can do”

Consider an operator that shares its services in a PDF. An agent can read the document and suggest a trip. That does not establish current availability, a working booking connection or the operator’s agreement to accept a reservation. Those are separate facts.

The earlier ATF report argues for reusable connections and a separation between model reasoning and enforced rules. The keel snapshot makes that distinction concrete: source descriptions become tools, and configured checks sit around their use. We use the earlier report as architectural context and the supplied code as the evidence for the behaviours discussed here.[1][2]

WHY IT MATTERSA tool that says “book” should not quietly mean “save a request for someone to review.”

2. Four boundaries before an action

First, describe the operation. A structured API specification can be compiled into tools with named inputs. For documents and prose, the snapshot provides a separate extraction API. That route requires an explicit authentication declaration and writes extracted material for review. The command-line builder does not support every input route end to end.[2]

Second, declare the connection. A callable-looking contract is not proof of a live transport. The documentation identifies contract-only cases and returns a structured explanation when execution is unavailable. The same principle matters for operators without booking systems: a recorded request must remain visibly distinct from confirmed inventory.

Third, check the call. Guardrails run before configured business rules, which run before the tool. Rules can permit, refuse, transform or escalate an action. A note in a prompt tells a model what to consider; this boundary determines whether a routed action may proceed. The checks only know the facts and policies supplied to them.[3]

Fourth, preserve the result. Keep the source, tool version and returned evidence connected to the action. When an upstream interface changes, compare it with the reviewed description. The snapshot supports drift checks; its document path does not silently regenerate and approve itself.[2]

4. Case study: the room has changed

ILLUSTRATIVE CASE

The answer sounds right. The offer is different.

A traveller approves a room with breakfast and a particular cancellation window. Before booking, the source returns a room without breakfast. An agent might still describe it as the same stay. The useful question is whether the actual offer still matches the approved purchase.

A configured check should stop the changed action and return a reason a person can understand. The proposed interface shows the changed inclusion beside the original approval. A new decision is needed before spending. This example illustrates the desired application behaviour; it is not a claim that every semantic difference is detected automatically.

MCP-Apps can give this boundary a visible surface: a comparison, a review card or a form connected to a tool result. The snapshot emits standard interface metadata as well as compatibility metadata. Whether the interface renders depends on the client that hosts it. A review button should pass through the same action checks as an agent call.[4]

6. An evaluation worth running

Build a labelled set of structured specifications, incomplete documents and deliberately changed offers. For each case, record what a reviewer believes the tool may do, then compare that with what the built tool advertises and executes.

TestUseful measurement
Remove access details from a document.How often construction stops before a callable tool is exposed.
Change an inclusion or cancellation term.Missed material changes and unnecessary requests for approval, counted separately.
Remove the live connection but retain its schema.Whether the UI and agent both report the operation as unavailable.
Change an API after review.Time to flag a breaking change and which calls remain permitted.
Repeat searches without progressing toward a booking.Requests per completed task, freshness and legitimate searches incorrectly blocked.

The final test addresses look-to-book pressure: repeated browsing must have limits without making useful search impossible. The appropriate budget depends on the connected service and the task. This paper proposes the evaluation; it does not report a measured improvement.

7. Limits and open questions

A valid schema can still describe an unsuitable purchase. A rule can enforce the wrong policy. A scan can miss an unsafe dependency. The supplied packaging guide explicitly limits its trust assessment to the controls it checks. None of these mechanisms establishes that every tool output is true.[5]

Operators without a booking system need a human confirmation route. Showing their services to agents is a useful first step, but automatic confirmation requires additional operational support. Similarly, post-booking care depends on available servicing operations and real evidence from the source.

The next research question is how to make capability and uncertainty understandable at the point of use. The user should see whether an action is a search, a request, a hold or a confirmed commitment—and what evidence supports that state.
