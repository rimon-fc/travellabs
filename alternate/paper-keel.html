Abstract

Keel addresses the production infrastructure needed to solve hard travel problems with agents. A declarative agent.yaml manifest compiles into a complete Model Context Protocol agent: gateway orchestration, skills, flows, entities, staged disclosure, interactive interfaces, authentication, interceptors, policy, state, audit, evaluations and packaging. This paper adapts the complete Keel chapter of the source implementation report, including its formal definitions, capability states and engineering examples.

Research objective: solving some of the hardest problems in travel with frontier AI. Adapted from the complete Keel chapter of Rimon Rony’s implementation report, 24 November 2026. Implementation claims and capability states are retained from that report; no new empirical evaluation is claimed.

Overview

A ship's keel is the load-bearing backbone, the single structural member every other part is fastened to. keel is that backbone for MCP agents: a production kernel that compiles one declarative agent.yaml into a complete running agent. No server code is written; the manifest describes what the agent is, not how to wire it. Formally, the kernel is a compilation function

k:𝒴→ℬ,k(y) defined only if valid(y)∧evals(y)∧trust(y) k : \mathcal{Y} \rightarrow \mathcal{B}, \qquad k(y) \text{ defined only if } \; \mathrm{valid}(y) \wedge \mathrm{evals}(y) \wedge \mathrm{trust}(y)

a partial function from manifest space to bundle space, defined exactly on the manifests that pass schema validation, the evaluation harness and the trust scan. The build is therefore a governed pipeline, not a packaging step.

In order to use keel: the keel-builder skill takes a plain-language prompt and builds the agent end to end; no YAML and no configuration file is hand-crafted. The manifest, entities, skills, flows, stages, evaluations and the trust-scanned bundle are all generated automatically (18).

This section is deliberately exhaustive; Table 1 is the ledger it substantiates, capability by capability. The frame for reading it is the four-beat order of the source report’s executive thesis: the kernel is 1 to 12, the compiler is 13 with the compile function above, governance is 8 to 11 with 15 and 16, and the protocol is the separate ATP paper; the remainder is proof of execution. Everything in the ledger is declarative infrastructure: declared in a manifest, compiled and enforced by the kernel, never wired by hand.

The contract behind all of it is one document. The manifest has around thirty top-level blocks, one per engine: auth, servers, guardrails, policies, routing, entities, skills, flows, constructs, stages, transitions, triggers, subagents, ui, execution, observability, evals, production, package, auto_build, atp, distribution, post_booking and runtime, each with typed fields, defaults and validation rules in a field-by-field reference. Three properties hold everywhere: unknown keys are rejected, so a typo fails at load time rather than being silently ignored; an absent block means the feature is off or in its safest mode, so the empty manifest is the safe manifest; and cross-field validation runs at load, a stage prerequisite must name a declared construct and an ATP supplier must name a declared server, so dangling references cannot survive to runtime. The CLI and the loader produce the same validated model, so what ships is what was checked.

What a connected client sees is equally disciplined. It never sees the manifest; it sees a small, stable meta-tool surface plus whatever the current stage discloses. Six meta-tools are always on: list_capabilities, use_skill, read_resource, run_flow, set_stage and state_set. Everything else appears only when the manifest opts in: the stage movers with declared stages, search_tools with large-catalog routing, the sandboxed execute with the python-sandbox execution mode, plan tools with the plan provider, delegate and list_subagents with declared subagents, the four task tools with async tasks, and six generated CRUD tools per declared entity. The visible surface is therefore itself a function of the manifest, which is what makes an agent auditable by reading one document.

1. Gateway and upstream servers

Declared: a servers: block aggregating HTTP, SSE and stdio upstreams into one catalog, with collision policy, allowlists and ${ENV} expansion. Meaning: one agent fronts many servers behind a single governed surface, so integration count stops scaling headcount and every upstream inherits the enforcement layers below. The flagship co-consult manifest shows the range: a managed remote MCP bridged over stdio, five providers autobuilt from OpenAPI specifications with per-request signers, and a vector-search MCP aggregated directly.

Spec 1 · Gateway · manifest-declared

declares an upstream set S={s1,…,sn}S=\{s_1,\dots,s_n\}, each si=(τi,ϵi,ai)s_i=(\tau_i,\,\epsilon_i,\,a_i) with transport τi∈{http,sse,stdio}\tau_i\in\{\text{http},\text{sse},\text{stdio}\}, or si=autobuild(speci)s_i=\mathrm{autobuild}(\mathrm{spec}_i) (Spec 9). Authentication aia_i is a per-upstream declared signer (bearer, query key, per-request HMAC); secrets enter only by environment expansion ε:$V↦env(V)\varepsilon:\ \${V}\mapsto\mathrm{env}(V), never as literals.

compiles one catalog C=⨄iN(si)C=\biguplus_i N(s_i) under a prefix collision policy, with the guarantee that every t∈Ct\in C is reachable only through the enforcement chain (9, 10). Instance: co-consult declares |S|=7|S|=7; five autobuilt, two bridged remote MCPs.

The engineering underneath is deliberately operational. Connections open lazily, so builds and offline evaluations stay green with every upstream down; each routed call carries a per-call timeout with one automatic reconnect, so transient drops are invisible and a hung upstream surfaces as a named timeout rather than a stalled agent. Per-server allowlists trim what an upstream may expose before anything downstream ever sees it, three collision policies (prefix, first-wins, error) make name clashes impossible by construction, and upstream credentials resolve through declared signers or connector references with token caching, never through anything inferred.

The gateway block also carries the catalog strategy for scale: a routing block namespaces large catalogs, per-server allow-lists cover resources as well as tools, and two fields turn an ordinary upstream into something more, a review pin gates an extracted source behind one-time human sign-off, and a conformance tier marks the same server entry as an ATP supplier, so commerce capability is declared in the gateway rather than bolted beside it.

The operational grain is worth stating. Aggregated names follow one convention, the server name, a double underscore, the original tool name, so provenance is legible in the name itself; connections open lazily and an unreachable upstream is skipped rather than failing the agent, which is why builds and offline evaluations stay green with every server down; a routed call carries a thirty-second timeout that names the server and tool on expiry, with one reconnect attempt before a failure is reported; resources are addressed by URI and bypass name-collision handling entirely; and every string in a server entry expands environment references, including a default form for unset variables, so secrets never live in the manifest.

2. Skills

Declared: SKILL.md files, optionally autoloaded per stage. Meaning: procedural knowledge served as skill:// resources, invoked through the use_skill meta-tool and exposed as /skill prompts. Value: the skill orchestrator turns operating knowledge into a governed, versioned artefact rather than prompt text pasted into a context window; co-consult's entire consultation brain is one skill autoloaded on the requirements stage. Alignment: skills discovery and distribution through MCP primitives is the subject of the official ext-skills repository (the Skills over MCP working group), which keel's skill:// surface tracks [11].

Spec 2 · Skills · manifest-declared

declares a versioned knowledge set KK and an autoload relation A⊆K×SA\subseteq K\times S over stages. compiles each k↦(skill://k,use_skill(k),/skill prompt)k\mapsto(\text{skill://}k,\ \mathrm{use\_skill}(k),\ \text{/skill prompt}), so the knowledge surface at stage ss is Ks={k:(k,s)∈A}K_s=\{k:(k,s)\in A\}, governed and diffable rather than pasted prompt text. Instance: co-consult's consultation brain is a single kk autoloaded at the requirements stage.

Two properties make skills safe to treat as an asset class. First, executable frontmatter is quarantined: any field that would imply running code is stripped and recorded inert, because a skill served over MCP is untrusted text, never code. Second, provenance is structural: skills synced from a repository carry a provenance sidecar (source, owner, ref, fetch time, executed: false) attached to the served resource, owner allowlists reject unexpected sources before any fetch, and pinned refs are never silently re-pulled. Skills can also gate themselves on the tools they need, disappearing cleanly from agents that cannot satisfy them, and version-adaptive bodies serve the right procedure to the right client version.

Discovery and gating are both mechanical. A generated index resource lists every skill with its URI, and a generated instruction nudge in the server instructions tells the model to activate the matching skill as its first action, so skill descriptions are written as triggers, not summaries. The requires gate is computed from the manifest itself, server names from the servers block, tool names from the union of allow-lists and stage lists, and a skill whose requirements are unsatisfied is simply never offered, no error, no placeholder. Directories are watched, so edits re-discover live. GitHub-sourced packs are governed before any network call: an owner allow-list rejects foreign repositories up front, tag and commit pins are never re-pulled, and every sync writes a provenance sidecar, recording source, ref and the fact that nothing was executed, which the runtime attaches to the served resource.

3. Flows

Declared: YAML graphs of entry, transform, switch, tool and exit nodes. Meaning: a flow is, in graph-theoretic terms, a directed graph

G=(V,E),V=Ventry∪Vtransform∪Vswitch∪Vtool∪Vexit G = (V, E), \qquad V = V_{\text{entry}} \cup V_{\text{transform}} \cup V_{\text{switch}} \cup V_{\text{tool}} \cup V_{\text{exit}}

whose execution is a single walk from the entry node to an exit node. A transform node has out-degree one and rewrites data (JSONata shaping); a switch node has out-degree greater than one and selects exactly one outgoing edge by evaluating JSON-Logic predicates over upstream node outputs, with a declared default edge so the walk is total; a tool node calls an upstream capability through the full enforcement chain. Node outputs are addressed by path ($.classify.priority), so every edge carries typed data, and the whole graph is schema-validated at build time. Termination is guaranteed by construction: execution.limits.max_node_executions bounds the length of any walk, so even a graph with back-edges cannot run away. The entire graph executes server-side as one run_flow call, and expose: tool optionally registers a flow as a first-class MCP tool with its own input schema. Value: deterministic multi-step work without exposing intermediate nodes to the model: the model sees one tool, the business sees one auditable graph, and both the attack surface and the token bill shrink accordingly.

Spec 3 · Flow · manifest-declared

declares the labelled graph G=(V,E,ℓ)G=(V,E,\ell) of Section 3, with switch routing δv\delta_v selecting exactly one outgoing edge by JSON-Logic predicate, total via a default edge.

exec(f, x):  w ← entry;  ctx ← {entry: x}
while type(w) ≠ exit:  ctx[w] ← eval(w, ctx);  w ← δ_w(ctx)
return ctx[pred(w)]            ▷ walk length bounded by the execution limit

Instance: the support-agent triage flow has |V|=7|V|=7, one switch, and folds three routes into one queue field.

Flows are also debuggable the way production infrastructure should be: an interactive controller exposes pause, single-step, breakpoints and time-travel inspection (the exact context an expression saw at any execution index) as meta-tools, so a mis-routed switch is diagnosed against real state rather than guessed at. A node may pause the whole flow until the caller supplies schema-validated input (the flow returns a structured input-required envelope, never an error), loops are first-class with per-node history accessors, and every run is bounded by manifest limits on node executions and wall-clock time.

Expressions inside a flow come in two governed dialects, JSONata for transformation and JSON-Logic for predicates, both evaluated without any general code execution; a switch must be total through its default edge, and the reference rejects a flow whose expressions name nodes that do not exist.

Beyond the graph itself sits a full authoring and debugging surface. Loops are first-class, with history accessors that read any earlier iteration of any node; two test meta-tools evaluate a JSONata or JSON-Logic expression against a supplied context without running the flow; an interactive debug controller starts a run paused, steps one node at a time, manages breakpoints and answers time-travel questions, the exact context an expression saw at execution index n; and a flow-authoring toolkit lists, edits and dry-runs flow tools, including an inline definition that is never persisted. Execution is bounded by manifest limits on total node executions and wall-clock time, and a node may pause the whole flow with a structured input-required envelope until the caller writes the named construct into session state.

4. Entities

Declared: JSON Schema per record type. Meaning: a generated, file-backed CRUD tool surface with relations, graph reads and seeding, plus a per-entity presentation.brief field list (6). Value: structured domain state without writing a persistence layer, and, in co-consult, provider neutrality: any supplier's flight-shop response is fanned into canonical fare_offer, flight_segment and fare_rule records by a declarative mapping, with the raw payload spilled losslessly behind a retrieve handle.

Spec 4 · Entities · manifest-declared

declares per record type a triple (σ,O,πb)(\sigma,\,O,\,\pi_b): a JSON Schema σ\sigma, operations O⊆{create,get,update,delete,list,search}O\subseteq\{\text{create},\text{get},\text{update},\text{delete},\text{list},\text{search}\}, and a brief projection πb\pi_b. compiles the typed CRUD surface {oσ}o∈O\{o_\sigma\}_{o\in O}; reads return πb(r)\pi_b(r) with a retrieve handle to the full rr (6). Instance: co-consult normalises every supplier payload into nine canonical types, the raw shop spilled losslessly behind the handle.

The store is more than six verbs. Records carry typed relations with a write-time reverse index, composite reads load a record plus its neighbourhood to a chosen depth with cycles cut, an activities trail records audit events against any record, seeding is idempotent on id so repeated builds never duplicate data, and lifecycle hooks map entity events to flows (a created ticket can notify the on-call flow declaratively). Server-managed base fields are stripped from the input schemas, so the model is never asked to invent bookkeeping.

The store semantics are stated rather than implied. Six tools per entity follow one naming convention with correct pluralisation; kernel-managed base fields are stripped from the input schemas so the model is never asked to invent an identifier or a timestamp; concurrency is last-writer-wins, named plainly as the v1 trade-off that keeps the generated surface dependency-free. Relations maintain a write-time reverse index that is rebuilt automatically when stale, composite reads walk both directions to a chosen depth with cycles cut and reverse edges keyed distinctly, activities are ordinary entities carrying a subject relationship so the audit trail rides the same index, seeding is idempotent on identifier so repeated builds never duplicate data, and lifecycle hooks dispatch flows best-effort, logged and never raised.

5. Stages, constructs and progressive disclosure

Declared: stages: scoping tools, skills and widgets, transitions: between them, and constructs:, named, schema-validated session state that gates entry. Meaning: the cart-before-checkout gate: a session cannot enter a gated stage until the required construct validates; until then set_stage returns KEEL_PREREQUISITES_UNMET and list_capabilities shows the gate up-front. The visible tool set at any stage is exactly TsT_{s}, so a client can never invoke a capability outside its current stage. Value: workflow correctness enforced structurally, not requested politely.

Spec 5 · Stages and constructs · manifest-declared

declares stages with a transition relation ⇝\rightsquigarrow and constructs cc with schemas σc\sigma_c. Gate rule: a transition s⇝s′s\rightsquigarrow s' is admissible at session state mm iff ∀c∈prereq(s′):m⊨σc\forall c\in\mathrm{prereq}(s'):\ m\models\sigma_c; otherwise the kernel refuses with KEEL_PREREQUISITES_UNMET and advertises the gate in list_capabilities. The visible tool set at any stage is exactly TsT_s; nothing outside it can be invoked. Instance: support-agent gates escalation on m⊨σticket_contextm\models\sigma_{\text{ticket\_context}} (Figure 4).

The refusal is the point. An inadmissible transition returns a structured payload naming exactly which constructs are missing, their schema summaries, and the state keys that satisfy them, never an exception; the agent reads the refusal, fills the named state, and retries. Stage state is isolated per session, every successful transition notifies the client to re-fetch its tool list, and a stage with no outgoing transitions automatically offers session termination.

The reference enforces the wiring statically: every prerequisite named by a stage must be a declared construct, so a gate that could never open is a load-time error, not a runtime surprise; transitions are a plain adjacency map, which keeps the whole disclosure graph reviewable in one screen of manifest.

Session mechanics are precise. Stage state is tracked per session through the declared header, while headerless transports share one stable default session so the stage survives across calls; every successful change emits the list-changed notification so clients re-fetch the tool list; a terminal stage swaps the advance tool for a terminate tool; and an ambiguous advance, several allowed targets and none named, returns a structured error rather than guessing. The prerequisite checker is a deliberate subset of JSON Schema, types, required fields, nested properties, enums and non-empty arrays, enough for every existence gate without a new dependency, and the refusal payload names each missing construct with a human-readable schema summary and the exact state key to fill.

A formal framing is available for readers who want one, restored here in prose rather than notation. An agent session has the structure of a partially observable Markov decision process (POMDP): the model never observes the true world state, only the conversation and tool results, and every tool call is an action against a state it cannot inspect directly. keel does not attempt to solve this decision problem and claims no optimality; its contribution is to shape the problem. The disclosure engine makes the action set a function of stage, A(s)=TsA(s) = T_s, and as established above the visible set at any stage is exactly TsT_s regardless of the path taken to reach it, a memoryless property engineered into the control surface rather than assumed of the world; the policy engine then prunes A(s)A(s) further, deterministically, before any action executes. The contrast with search-based planning is deliberate: where planners in the Monte Carlo Tree Search (MCTS) family choose actions by exploring many simulated futures, a governed booking surface has no cheap simulator, real tool calls carry real side effects, so keel constrains the single real trajectory rather than searching hypothetical ones: constraint over search.

6. Presentations

Declared: presentation.brief per entity and per result. Meaning: context-cheap brief summaries carrying retrieve handles; nothing lost, only deferred. Context is a finite resource that agentic systems must engineer deliberately [6], and this feature makes that engineering declarative: co-consult's flight searches return a compact brief keyed by shop_id while the megabyte-scale raw payload waits behind the handle.

The numbers are deliberately small and pinned by tests: a brief record is the id plus three scalar fields (or the manifest-declared projection), a brief list is five reduced items plus a total, and a twenty-record list that would dump thousands of characters serialises to under eight hundred, with the full payload one verbatim retrieve call away. Diagnostics are never reduced, and write results are always complete.

The reducer is chosen by payload shape, an entity keeps its identifier plus the declared or first three scalar fields, a list keeps five reduced items plus a total, a flow result keeps status, output and the node and step counts, and an error envelope is never reduced, diagnostics always arrive whole. The budgets are pinned by tests: twenty seeded records each carrying a long description serialise, brief, to under eight hundred characters. The retrieve contract is verbatim, call the named tool with the supplied arguments unchanged and the full payload comes back with no marker and no handle, and the renderer itself is pure standard library, callable from any custom tool.

7. UI widgets

Declared: MCP-Apps ui:// resources with a sandboxed host page and a dashboard widget-host emulator, for example support-agent's ui://ticket-card rendered inline with the tool result. Alignment: this implements the official MCP Apps extension, SEP-1865, maintained in the modelcontextprotocol/ext-apps repository [11], so keel widgets are standard, not proprietary surface.

Spec 6 · UI widget · manifest-declared

declares w=(uri:ui://…,mode,entrypoint,display)w=(\text{uri}:\ \text{ui://}\dots,\ \text{mode},\ \text{entrypoint},\ \text{display}), rendered only inside the sandboxed host page, optionally inlined with the tool result that produced it. The declaration conforms to the MCP Apps extension, SEP-1865 [11]; nothing about the widget is proprietary surface.

Widgets ship in both wire dialects at once, the standard MCP Apps form and the legacy form side by side, so the same declaration renders in compliant hosts today and older hosts through migration. The production host page runs a deny-by-default sandbox (no same-origin privileges), per-widget content-security domains are declared in the manifest, UI-only tools are callable from inside a widget but invisible to the model, and a built-in host emulator with a live in-process server makes widget development possible without any real host on the laptop.

The ui block covers more than widgets: configuration apps let an operator adjust declared settings from inside the host, and a client bridge lets a widget call back into the agent through UI-only tools, so an interactive surface can be genuinely interactive without ever widening what the model itself can call.

The wire format is dual by default. Widgets emit the standard MCP-Apps form, a profiled HTML MIME type with a ui metadata block, alongside the legacy keys older hosts still read, with one environment variable or manifest field selecting either alone; the production host page renders every widget in a sandboxed iframe that deliberately withholds same-origin, a bridge endpoint carries initialise, tool calls (including UI-only tools hidden from the model) and resource reads, and an opt-in event stream live-refreshes open widgets on every new execution record. The development emulator is the honest inverse: it relaxes the sandbox so a dependency-free shim can proxy tool calls to the live in-process server, acceptable on a development page and exactly what the production page never does.

8. Authentication

Declared: dev, JWT, API key or OAuth 2.1 caller auth (auth: { provider: dev } in the offline examples), TTL sessions, and upstream connectors with token exchange and per-request signers, Spec 1 records the three declared signer shapes, a bearer bridge, a query-key signer and a per-request HMAC signer. Alignment: the authorisation surface tracks the official ext-auth extension repository, OAuth client credentials and enterprise-managed authorisation [11].

The auth surface runs both directions and is standards-literal. Inbound, the agent is an OAuth 2.1 resource server with published protected-resource metadata and a built-in token endpoint (client-credentials, three client authentication methods, resource indicators, scope enforcement); dev, JWT and API-key postures cover every deployment stage below that. Outbound, connectors obtain upstream bearers through pre-issued tokens or live client-credentials flows with expiry-aware caching, and an enterprise block enables the RFC 8693 token-exchange chain, corporate identity in, audience-scoped access out, for enterprise-managed authorisation. Secrets never appear in a manifest; every credential arrives from the environment at runtime. This is the procurement unlock: the security review reads a standards-conformant architecture and passes, instead of stalling the engagement while one is retrofitted.

The reference makes the auth surface precise: four provider postures (dev, JWT, API key, OAuth 2.1, the last also mounting the RFC 9728 protected-resource and token routes), identity-bound sessions with a TTL and a declared header, four client authentication methods including RFC 7523 private-key JWT, RFC 8707 resource indicators, and per-connector enterprise federation blocks, each individually enableable, so one manifest can hold a corporate token-exchange connector beside a plain bearer bridge.

Connector resolution is a fixed order with the cheap path first: a pre-issued token from conventional environment names, no network, then a live OAuth 2.1 client-credentials flow against the declared endpoint, with per-connector credentials falling back to the generic pair and tokens cached until shortly before expiry so repeated upstream calls never re-hit the identity provider. A rejected caller receives the RFC 9728 challenge naming the metadata document, so discovery is part of the refusal itself.

9. Interceptors

Declared: a guardrails.interceptors chain of validators and mutators bound to event patterns and phases. Meaning: enforcement wraps every call, which matches the emerging design consensus that injection defence must constrain what tool calls can do rather than what the model is asked to do [7]: adversarial context reaches the model; it must not be able to reach the tools. Alignment: interceptor semantics are under standardisation in the org's experimental-ext-interceptors repository [11].

The mechanics matter as much as the placement. Each interceptor is named, has a kind (a validator, which can reject an event, or a mutator, which rewrites it), binds to event patterns (tools/*, resources/*) and to a phase (request or response), and the chain composes in declaration order around every call, including calls to autobuilt tools and aggregated upstream servers, so complete mediation holds: there is no path to a capability that bypasses the chain. The two shipped patterns in Spec 7 show the division of labour: a request-phase validator blocks injection before a tool ever runs, and a response-phase mutator redacts PII before a result ever reaches the model's context. Because interceptors are declared in the manifest, a change to the security posture is a reviewable diff and a rebuild, never a prompt edit.

Spec 7 · Interceptor chain · manifest-declared

declares an ordered chain I=⟨i1,…,in⟩I=\langle i_1,\dots,i_n\rangle, i=(kind∈{validator,mutator},events,phase)i=(\text{kind}\in\{\text{validator},\text{mutator}\},\ \text{events},\ \text{phase}). Request semantics: r′=(in∘…∘i1)(r)r' = (i_n\circ\dots\circ i_1)(r), where any validator may map to ⊥\bot (reject); response semantics are dual. Complete mediation: the domain is every tools/* and resources/* event, autobuilt upstreams included. Instance: co-consult runs an injection validator on request and a PII mutator on response.

Deployment of a new guardrail is itself governed: audit mode shadows the entire chain against production traffic, logging violations and computing mutations without applying or blocking anything, so a new interceptor is trialled on real load before it is allowed to say no. Per-interceptor fail-open and chain-wide defaults make the crash semantics explicit, and a blocked call surfaces as a structured verdict naming the guardrail, never as a mystery failure.

Chain mechanics reward attention. Request-phase mutators run sequentially in priority order before validators run logically in parallel; response-phase validators run before mutators, so redaction is the last thing to touch a payload on the way out. Only error-severity findings block, warnings and informational findings are logged; a crashing interceptor follows its declared fail-open or fail-closed posture, per interceptor or chain-wide; and an audit mode shadows the entire chain against production traffic, computing verdicts and mutations without applying or blocking anything, which is how a new guardrail is trialled safely before it gates anyone.

10. Policy engine

Meaning: deterministic business rules evaluated around every tool call. Where interceptors (9) protect the system, the policy engine encodes the commercials: this is where a travel business writes down, as code rather than prompt text, the rules it already runs on. Concretely: fare-tier rules (a consumer-tier trip cannot commit a business-class fare; a corporate profile books refundable fares only); margin rules (a proposal whose blended margin falls below the floor is blocked or escalated for approval rather than sent); supplier-hierarchy rules (mandatory primaries are searched before advisory context sources ever influence a recommendation); spend ceilings per booking and per customer; and consent rules (no ATP commit path exists without the the separate ATP paper.1 consent event). Because the rules are deterministic middleware, they hold identically for every model, every prompt and every session; a pricing rule changed in the manifest changes everywhere at the next build, with the old and new behaviour separated by one reviewable diff. Value: the governance claim of the stack in one sentence:

The model can ignore context. It cannot bypass middleware.

The failure semantics are the contract. A deny rule whose precondition cannot be evaluated fails closed, because an unverifiable precondition must not permit a commercially binding action; a broken transform fails open with an audited error, because an enrichment must not take the surface down; a missing or broken engine backend fails closed on every applicable call with a structured envelope, never a silent permit. Expressions are evaluated by a safe AST walker, there is no eval anywhere, and payment-mandate claims carried in a traveller token are enforced as implicit deny rules (amount caps, scope checks) ahead of every configured rule.

The evaluation contract is exact. Each rule sees two namespaces, per-call facts (tool, arguments, session and the merged output of context providers, which resolve as state lookups, entity lookups or flows, with a bare name falling back to a state key, the path by which live margin facts arrive) and static rules values. The expression evaluator is a safe AST walk, no eval anywhere, calls, subscripts, comprehensions and lambdas rejected before evaluation. The first deny or escalation short-circuits; transforms accumulate into the arguments later rules and finally the tool receive. Audit records drop argument strings past two hundred and fifty-six characters, a PII-light snapshot by construction, and the middleware installs only when the manifest activates the surface, so an unconfigured policies block adds zero overhead.

11. State and audit

Declared: a pluggable StateStore (memory, sqlite, Postgres, Redis) and an append-only audit sink. Records are hash-chained,

hi=H(hi−1‖ri) h_i \;=\; H\!\left(h_{i-1} \,\Vert\, r_i\right)

so tampering with any record rjr_j invalidates every subsequent link, by second-preimage resistance of HH. The guarantee is relative to a trusted head: a rewriter of rjr_j can recompute a consistent forged suffix, so detection reduces to comparing the current head against one recorded outside the writer. This is the property an auditor actually wants: not a log, a tamper-evident chain.

The chain mechanics are simple enough to audit by eye: each record hashes its predecessor from a fixed genesis, the canonical serialisation is byte-stable across processes, the module issues only create, insert and select statements (append-only by construction, asserted by tests against the source), and a single verify call re-walks the whole chain and names the first broken row. One pluggable key-value spine carries every kind of durable state, sessions, stage state, task records, so moving from in-memory to SQLite, Postgres or Redis is one manifest line, not a rewrite.

The persistence spine degrades predictably: an unreachable Redis logs and falls back to memory rather than failing the build, a Postgres backend without a connection string degrades the same way, and the drivers import lazily so constructing a store never touches disk or network. Key namespaces keep tenants of the spine apart, disclosure state, auth sessions, durable tasks and the replica session registry each under their own prefix. The chain itself is small enough to audit by eye: each row hashes its predecessor together with a canonical, byte-stable serialisation of itself, the genesis link is sixty-four zeros, and the module issues only create, insert and select statements, a property asserted by tests against the module source. Verification names the first broken row and the reason, and an append failure never crashes the tool call that triggered it, the execution log stays the operational record while the chain stays the tamper-evidence layer.

12. Tasks, triggers and subagents

Declared: durable pollable tasks that outlive a conversation turn; event and cron triggers that run flows with no human in the loop; and named subagent personas with narrowed capability surfaces, the orchestrator-plus-specialists pattern that multi-agent systems research has converged on. Alignment: long-running task semantics track the official ext-tasks extension, and trigger and event semantics the org's experimental-ext-triggers-events repository [11]. flight-deal-watcher is the working example: an entity.changed trigger and a cron poll both drive the same flow and post hits to a webhook.

Spec 8 · Triggers and tasks · manifest-declared

declares T={(e,φ,f,κ)}T=\{(e,\ \varphi,\ f,\ \kappa)\}: event source e∈{entity.changed,cron(expr)}e\in\{\text{entity.changed},\ \text{cron}(\text{expr})\}, guard φ\varphi in JSON-Logic, flow ff, sink κ\kappa. Semantics: on ee with φ(e)\varphi(e), execute ff on the event payload and append to the audit chain hih_i; durable tasks are pollable state machines outliving a turn [11]. Instance: the deal watcher declares two sources, one flow, one webhook sink.

Three details carry the weight. Durable tasks have a real lifecycle (working, input-required, terminal states) with cooperative cancellation and capability negotiation, a task handle is never given to a client that cannot poll it. Delegation serves a subagent from a projected surface where out-of-scope tools are absent, not refused: even a prompt-injected call to a forbidden tool fails because the tool does not exist there, and the delegated prompt is wrapped as data beneath the persona instructions, so a task that tries to redefine the persona lands inside the data block. Cron uses a real five-field parser with macros, triggers guard on typed events with predicate conditions, and webhook sinks report outcomes without ever being able to crash the server.

The details are protocol-faithful. Task lifecycle is a real state machine, working to input-required and back, then one of three terminal states, with expired records lazily reaped; a server never hands a task handle to a client that did not declare the tasks capability, refusing with the specified error code, and an unknown task identifier returns the invalid-params shape rather than a stack trace. The cron parser is standard-library and complete, lists, ranges, steps, names and macros, with the traditional either-or semantics when both day fields are restricted, and a malformed expression is logged and skipped, never aborting the agent. Trigger webhooks post outcomes and never crash the server on failure. Delegation is containment engineering: the delegated prompt is wrapped as data inside an envelope the persona instructions sit outside of, a projected persona cannot re-delegate, and with no executor available the call degrades to a delegation context the caller can run itself, stated in the result rather than hidden.

13. Autobuild: the auto MCP server builder

Declared: a servers: entry pointing at an API specification, OpenAPI, GraphQL, AsyncAPI, Protobuf, Postman or Smithy, or at unstructured documentation, with build knobs under auto_build:. Meaning: keel compiles the specification into typed MCP tools at build time; nobody hand-writes an integration server. Every specification is vetted through the guardrail chain on each load, authentication is never guessed, and unstructured sources require review before caching. Value: the marginal cost of a new integration approaches the cost of pointing at its spec; five of co-consult's seven upstreams are autobuilt.

Spec 9 · Autobuild · manifest-declared

declares a source specification and compiles the mapping 𝒜:Specfmt→Tools\mathcal{A}:\ \mathrm{Spec}_{\mathrm{fmt}}\rightarrow \mathrm{Tools}, fmt∈{OpenAPI,GraphQL,AsyncAPI,Protobuf,Postman,Smithy,docs}\mathrm{fmt}\in\{\text{OpenAPI},\text{GraphQL},\text{AsyncAPI},\text{Protobuf},\text{Postman},\text{Smithy},\text{docs}\}, with two invariants: vet∘𝒜\mathrm{vet}\circ\mathcal{A} runs on every load, and authentication is a declared signer, never inferred; unstructured sources additionally require human review before caching. Consequence: the marginal cost of an integration approaches the cost of pointing at its specification.

The pipeline is disciplined about trust. The registry is consulted before any compile, so a known-good contract is never re-derived; every built tool is routed through the interceptor chain on every load, so a specification poisoned after first vetting is still caught on reload; authentication is never guessed, an unstructured source with no valid declared auth scheme refuses to build at all, with a structured envelope naming the gate, before any extraction model is even consulted. Extracted specifications are pinned for one-time human review with a recorded digest, and a scheduled drift checker re-derives each source against its pin under a per-day budget, publishing honest events for both detected drift and budget-exhausted skips.

The source-kind list is wider than the structured formats: beside OpenAPI, GraphQL, AsyncAPI, Protobuf, Postman and Smithy sit lap (a registry of already-built contracts, consulted by name), docs, pdf, curl and portal, the messy sources a travel business actually has, and exactly these unstructured kinds are the ones the review-pin gate exists for: extraction proposes, a human pins, and the pin carries a digest.

The pipeline is six steps with the safety in the middle: sniff the kind, consult the registry first (a hit skips compilation entirely, though a local file stays authoritative), compile to the intermediate contract, derive typed tools, then route every derived tool through the interceptor chain, on every load, so a cached or registry-sourced spec poisoned after its first vetting is still caught on reload, and finally record provenance. Extraction from unstructured sources validates and repairs the model output up to a bounded number of attempts and refuses stubs that fail sanity, embedded script markers, oversize documents, implausible path counts, before anything downstream sees them. Auth has no bypass flag: the gate fires before any extraction runs, so nothing a model claims to have seen in the documentation ever counts as a declaration. Drift is evented and budgeted, a detected change publishes a typed report with severity, an exhausted daily budget publishes an honest skip event, never a silent one.

14. Runtime

Meaning: keel-runtime is the standalone agentic loop that actually drives the agent: it plans, calls tools and observes results in a turn loop [1], with pluggable LLM providers (an offline mock by default, requiring no API key) and optional external executors. This is what makes keel run work without wiring an LLM by hand.

Algorithm 1 · keel-runtime plan-act-observe loop
Input: goal g, manifest-compiled agent A, provider P, budget B
1:  ctx ← initialise(g, A.meta_tool_surface)
2:  while not done(ctx) and cost(ctx) < B do
3:      plan ← P.next(ctx)                        # language or tool action
4:      if plan is tool_call(t, x) then
5:          assert x in X_sigma(t)                 # schema-valid by construction
6:          v ← enforce(auth, guards, policy, t, x)   # Section 5
7:          if v = ALLOW then r ← t(x); audit(h, r)
8:          elif v = ASK then r ← await_human(); audit(h, r)
9:          else r ← denial(v.reason); audit(h, r)
10:         ctx ← observe(ctx, present(r))        # brief + retrieve handle
11:     else ctx ← observe(ctx, plan)
12: return transcript(ctx), audit_chain(h)

Honesty about coverage is built into the runtime tier itself. The in-process paths wrap every tool call in the guardrail chain; the external harness paths wrap only the agent's MCP surface, and the agent reports which posture it is running under rather than letting anyone assume. A mock brain is always an explicit choice, never a silent fallback; live harness paths are gated behind an explicit environment opt-in so CI can never accidentally spawn one; and elevated permissions require an explicit sandbox decision in the manifest, enforced again at run time, before any child process is spawned.

The execution tiers are honest about their differences. The provider factory never substitutes the mock silently; with no key configured it raises a named error telling the operator to pass the mock explicitly for offline runs. The subscription lane routes through a local proxy with a literal placeholder in the key field, never a secret, and fails fast at construction when the proxy is down, naming the compatible version. The Claude Code executor passes the prompt on standard input rather than the command line, mounts skills and the agent’s own MCP surface through the harness configuration, and retries an expired session once with full replay; the Codex path has no resume and no skill or MCP wiring, a real gap that is documented rather than faked; spawning any external harness at all requires an explicit environment opt-in, so CI can never do it by accident. Elevated permissions demand an explicit sandbox decision at load time and are re-asserted at run time with a structured refusal, and every capability listing reports which guardrail coverage the chosen executor actually provides, full for the in-process paths, MCP-surface-only for external harnesses.

15. Observability and evaluations

Declared: observability: (Prometheus at /metrics, OpenTelemetry tracing, PII-sanitised signals, an execution log with retention, a live dashboard) and evals: (a directory of offline evaluation cases with assert markers). All seven shipped examples are built and evaluated in continuous integration; benchmark practice for tool-agent evaluation in commerce-like domains follows the tool-agent-user setting, whose airline domain is directly adjacent to ATP [9].

The eval harness is deliberately deterministic: tasks name the exact tool, resource or flow to exercise, so they run with no external model, fully offline, identical in CI and on a laptop, over the real MCP protocol via an in-process client, and the command exits non-zero on any failure, which is the entire CI story. Telemetry redacts secrets and personal data before anything is persisted, by default; Prometheus counters and optional OpenTelemetry spans come from the same records that feed the operator dashboard and, opt-in, the audit chain.

The operational grain: four labelled counter families render in the Prometheus text format with no hard dependency on the client library; sanitisation runs before anything persists, redacting values under sensitive key names and scanning strings for addresses, emails and token shapes; the execution log is a write-ahead-logging SQLite by default, a bounded in-memory ring when asked, and a declared-but-unwired Postgres option that degrades with a log line rather than pretending; a write failure is swallowed rather than crashing the call. The dashboard exposes the records, sessions and a live event stream over a handful of routes, and doubles as the widget emulator described under the UI capability.

Task mechanics make determinism concrete. A task names its action outright, a tool call with arguments, a resource read, a prompt render, a flow run, an importable entrypoint or a file read, so no external model is needed to produce output; markers are matched as case-insensitive substrings, no markers means any non-empty output passes, and a task with neither action nor file falls back to asserting against the discoverable tool names, so even the surface itself is testable. The combined mode runs a task both over the protocol and in-process and passes only when both pass, the strongest signal that behaviour is transport-independent, and the command exits non-zero on any failure, which is the entire continuous-integration story.

16. Packaging and trust

Declared: package: { format: mcpb, min_trust: L2 }. Meaning: compilation to a portable .mcpb bundle is gated by an MTF-style trust scan at publish and re-run at install, with a declared minimum trust level; the bundle format itself is the org's official mcpb specification, not a private container [11]. Shipping is a permission the build earns.

The trust scorecard is honest about its own reach: eight real controls across the five trust-model domains are evaluated (secrets, dangerous patterns, dependency pinning, bundle completeness, declarations, provenance), the computed level is capped at the standard tier no matter how clean the bundle, and the scorecard records that the level is based on a control subset. A manifest demanding a floor the scanner cannot attest fails loudly at build, not quietly at publish. The same scan runs again at load and install time, so a dependency bundle that has rotted or been tampered with is refused with an actionable error naming the failing controls.

The mechanics are unambiguous. The eight controls are named and span all five trust-model domains, manifest validation, bundle completeness, dependency manifest and pinning, secret detection, dangerous-pattern detection, tool declaration and source provenance; a level passes only when every control at or below it passes; and the scorecard carries its own honesty markers, a subset basis field plus counts of controls evaluated against the full catalogue. A floor the scanner cannot attest fails at construction, not at publish, with a message that says exactly why and what to do; a bundle below the floor is refused with a structured result naming the levels; and the consume-side gate raises a typed error carrying the scanned level, the required floor and the full report, so a refusal is always actionable.

17. Registry

Meaning: publish and install bundles with end-to-end SHA256 integrity; a local FileRegistry is the self-contained default today, and the integration target is the official MCP Registry, the org's hosted discovery service with namespace-authenticated publishing [12].

Integrity is verified at every touch, not just at upload: the artefact digest is recorded when published, re-checked on every read, and re-checked twice on install (the stored copy and the installed copy), with a failed copy deleted rather than left behind; index writes are atomic, so a crashed upload can never leave a half-written registry. The default backend is a plain directory with no server and no credentials beyond filesystem permissions, and a remote registry swaps in behind the identical publish flow with an OIDC token exchange.

Integrity is enforced four times, not once. The index is written atomically by temp-file replace so a crashed upload never leaves a half-written index, and the artefact is stored before its entry so an entry never points at a missing file; digests are verified at upload against the declared hash, on every read before bytes are returned, and twice on install, the stored artefact and then the installed copy, with a failed copy deleted rather than left behind. Three exception classes separate not-found from corruption from everything else. The remote client follows the standard OIDC publishing pattern, a token exchange for short-lived credentials then a multipart upload, and its HTTP dependency imports lazily so nothing touches the network until a real remote publish runs.

18. Extensions and the keel-builder skill

Extensions: one register(mcp, manifest, ctx) hook with entry-point discovery is how verticals plug in; ATP (the separate ATP paper) is itself an extension, and the proposed conversation extension (the source report’s roadmap.1) follows the same pattern. keel-builder: the natural-language doorway. A skill-capable assistant pointed at skills/keel-builder/ takes a plain-language brief, routes it, scaffolds the project, composes entities, skills, flows, stages, UI and auth, autobuilds servers from APIs or documents, packages and trust-scans the bundle and verifies it with the evaluation harness, returning a runnable agent folder. The brief is the interface; the manifest is the artefact.

The discipline is what makes third-party capability safe: registration is unconditional but activation is manifest-driven (an extension whose block is absent must do nothing), a failing import or a raising hook can never crash server startup, the manifest forbids unknown top-level keys so a typo fails loudly and an extension cannot invent configuration, and the kernel's own engines load through the same mechanism in a fixed order, guardrails first so they wrap everything, UI last so it can see everything.

The loader rules are what make the surface safe to open. Registration happens once per build, after fifteen kernel built-ins that load in a fixed order, guardrails first so they wrap everything, UI surfaces last so they can see every registered tool; entry-point extensions then load sorted by name for determinism, with an installed package winning over the in-tree fallback of the same name. A module that fails to import is skipped quietly, and a registration hook that raises is logged and skipped, an extension can never crash server start-up. Because the manifest rejects unknown top-level keys, a third-party vertical cannot invent configuration; it gates on what it owns and follows the same rule as the kernel, no configuration, no effect, so installing an extension never changes behaviour until a manifest opts in.

19. SEAM: the honesty model

Every capability boundary in a keel build is a seam in exactly one of three states: real (implemented and on by default), guarded (dormant until an extra dependency, environment variable, flag or configuration key is satisfied) or absent (declared in contracts but not implemented, surfaced through validation errors and stubs, never faked). keel seams prints the honesty table for the build, sourced from SEAMS.toml; keel status prints the wired state of the install.

keel never silently pretends. A capability register the kernel itself reports is a board-level trust property, not a developer convenience.

The CLI is the compiler made operable, eleven verbs with one discipline: init scaffolds the conventional layout, build compiles and bundles, run serves with the UI host and metrics attached, serve is the stdio-only sibling that writes nothing to standard output except the protocol itself and is therefore safe to spawn as a child, eval runs the harness and exits non-zero on any failure, publish runs the trust scan and refuses below the floor, ingest, build-server and drift drive the auto-builder (drift exiting non-zero on a breaking change), seams renders the honesty register of what is real, guarded or absent in the installed build, and status is generated live from test artefacts, discovered extensions and the seam register, never a hand-written document that can rot.

20. Structured-output alignment: riding the trained distribution

Everything in this section reduces to one pattern: keel rides the JSON Schema interface that frontier models are post-trained against [4,5], and that API providers now enforce as structured outputs [3]. The manifest is validated against agent.schema.json; entities are JSON Schema in, CRUD tools out (4); flows are shaped by JSONata and routed by JSON-Logic (3); autobuilt servers are typed tools compiled from schemas (13); and every MCP tool contract the client sees is JSON Schema by specification [2]. The platform therefore operates inside the exact output distribution the models were trained to produce (the source report’s structured-output analysis), which converts directly into call reliability. This is the stack's primary differentiator; its economic weight is analysed in the source report’s standards-economics analysis.
